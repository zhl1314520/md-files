## 📌在 UI 自动化中元素定位与等待机制导致的用例不稳定

#### 背景

- 多嵌入动画页面点击&输入偶发性断言失败，但是手动点击的话又可以成功

#### 尝试排查

- 在脚本用例中添加日志、print 
- 找到问题：页面元素还没完全加载完成，就去获取列表元素数量了

#### 解决

- 引入显示等待

- 优化定位方式：
  1. find_elements() ——> 先定位列表容器、再获取子元素
  2. 封装等待方法进行工程化

## 📌在接口自动化中 429 token 鉴权失败问题

#### 背景

- 后端设置 5 分钟内最多只能使用 3 次 频率
- 用例执行使用的是同一个 token
- 导致部分接口断言失败

#### 排查

- 日志：有个接口响应时间很慢，批量跑用例导致超时

#### 解决

1. 后端加长 token 频率时间
2. 引入 token 池（亮点🔥）——轮询策略
3. 限速执行（每秒一个请求）

## 📌UI 案例：接口"假成功"问题

提交表单——前端提交，没有报错——但是后端没有数据落库

排查：

- 前端抓包——没问题
- 后端接口——postman 没有报错，但数据库中没有数据

- 日志无误

解决：

- redis 缓存问题，其实事务未真正提交

## 📌UI 案例：多次提交问题

表单数据同个账号可以多次提交问题

- 如何发现：
  - 在数据库中发现相同数据问题
- 排查：
  - 前端没有做防止重复提交限制
- 解决：
  - 前端设置防止重复点击限制
  - 后端幂等校验（同个请求执行多次结果一样）
