## 📌内存泄漏及原因

内存不用了但没释放。

原因：

- 对象引用未释放
- 集合不断增长
- 数据库连接未关闭
- 死循环创建对象

结果：
 内存越来越高，程序变慢甚至崩溃。

## 📌状态码

### 3XX

- **301 Moved Permanently**：资源被永久转移到一个新的URL。
- **302 Found**：资源临时转移，常用于登录后跳转

### 4XX

- **400 Bad Request**：请求语法错误，服务器无法理解。
- **401 Unauthorized**：请求未授权，需要身份验证。
- **403 Forbidden**：服务器理解请求，但拒绝执行。
- **404 Not Found**：服务器找不到请求的资源

### 5XX

- **500 Internal Server Error**：服务器内部错误，无法完成请求。
- **502 Bad Gateway**：网关或代理服务器从上游服务器收到无效响应。
- **503 Service Unavailable**：服务器超载或停机维护，无法处理请求

## 📌如何用ping命令测试网络连通性？它的工作原理是什么？

`ping <目标IP或域名>`。如果能收到`Reply from ...`或`64 bytes from ...`的回应，说明网络是连通的。

原理：**ICMP** 协议，向目标主机发送一个ICMP Echo Request（回显请求）报文，目标主机收到后回复一个ICMP Echo Reply（回显应答）报文。根据是否收到回复以及回复时间，可以判断网络连通性和延迟。

## 📌TCP 三次握手

目的：建立可靠连接。

过程：（SYN 和 ACK 是 TCP 报文中的标志位）

- 第一次：客户端向服务器发送一个`SYN`报文，表示请求建立连接
- 第二次：服务器收到后，回复一个`SYN+ACK`报文，表示已收到请求并同意建立
- 第三次：客户端收到后，再回复一个`ACK`报文，确认连接建立

## 📌TCP 为什么不是两次握手？

- 如果只有两次：

​			客户端发送的旧 SYN 可能滞留网络。

​			服务端收到后会误认为客户端要建立连接，造成资源浪费。

- 三次握手可以确认：

​			客户端收发正常

​			服务端收发正常

​			因此更可靠。

------

## 📌TCP 4 次挥手(断连过程)

#### `因为 TCP 是全双工通信，双方都可以发送数据，所以关闭连接时需要双方分别关闭`

第一次：客户端发送一个`FIN`报文，表示自己没有数据要发送了，请求关闭连接

第二次：服务器收到后，回复一个`ACK`报文，表示知道了，但可能还有数据要发，此时连接处于“半关闭”状态

第三次：服务器数据发送完毕后，向客户端发送一个`FIN`报文，表示同意关闭连接

第四次：客户端收到后，回复一个`ACK`报文，然后等待一段时间（2MSL）后彻底关闭

## 📌 浏览器输入网址后的过程

1. DNS 解析域名得到 IP 
2. 建立 TCP 连接（三次握手）
3. 浏览器发送 HTTP 请求
4. 服务器处理请求并返回响应
5. 浏览器解析 HTML/CSS/JS 渲染
6. 断开连接（四次挥手）

## 📌如果Web服务器响应很慢，从哪些网络层面排查

1. **客户端侧**：用浏览器F12开发者工具（Network面板）查看具体是哪个接口耗时最长，是请求排队、等待响应还是内容下载慢。
2. **网络侧**：用`ping`命令检查基础网络延迟和丢包情况。用`traceroute`或`pathping`命令查看从客户端到服务器的路由轨迹，定位可能的网络瓶颈节点。
3. **服务器侧**：用`top`或`htop`看服务器CPU、内存负载是否过高。用`netstat -an`统计服务器处于`TIME_WAIT`状态的连接数量，判断是否是短连接过多导致端口耗尽。
4. **应用侧**：检查应用服务器（如Nginx、Tomcat）日志，看是否有慢查询或代码错误记录。

## 📌TCP 流量控制

目的：防止发送过快导致接收方处理不过来。

核心：

- 滑动窗口机制

接收方告诉发送方：

```
我还能接收多少数据
```

发送方根据窗口大小发送数据。

## 📌 HTTPS 中 SSL 层原理

### SSL/TLS 作用：

- 加密
- 身份认证
- 数据完整性

### 流程：

1. 客户端发起 HTTPS 请求
2. 服务端返回证书（公钥）
3. 客户端验证证书
4. 客户端生成随机密钥
5. 用公钥加密后发送
6. 服务端用私钥解密
7. 双方使用对称加密通信

核心：

```
非对称加密传输密钥
对称加密传输数据
```
